# Selected improvement CLI contract

All commands use `coverage_audit.py --workspace ROOT COMMAND --context CONTEXT --FLAG FILE`.
Inputs and evidence files stay inside ROOT. Audit contexts stay under `outputs/mcp-coverage-audit`.
New contexts are version 2; recorded version 1 remains on its historical workflow. Nothing executes evidence.

## Proposal (`propose --proposal FILE`)

```json
{
  "job_state": "completed",
  "capability_assessment": "Atomic CAD coverage was complete; no missing live primitive was found.",
  "efficiency_assessment": "The same inspection required repeated calls; a bounded summary removes repetition.",
  "candidates": [{
    "id": "summary",
    "title": "Persist the bounded audit summary",
    "benefit": "Avoid repeating audit reads.",
    "evidence": "The completed CAD audit repeated the same status read.",
    "scope": "Local hook and CLI reporting only.",
    "acceptance": "A real disposable CLI run returns the persisted summary.",
    "verification_route": "hook_cli"
  }]
}
```

Use `verification_route: "live_tool"` plus `tool: "inspect"` for a CAD capability. This route must later demonstrate the named actual live tool and changed behavior, with current source hashes.
Both assessments are required. Candidate IDs are unique, at most 80 characters; other required text is at most 1,200 characters. Maximum 12 candidates. Routes are exactly `live_tool` or `hook_cli`.
For no candidates, use `candidates: []` and required `no_candidate_reason`. For unfinished CAD, use only `job_state` in `unfinished|paused|cancelled|superseded|higher_priority` and a bounded `reason`. Coverage must be finished before the first completed proposal when observed events require coverage.

The response contains `proposal_id`, normalized `candidates`, `display`, `context`, and `status`. Display the returned numbered `display` in the final CAD response. It contains each ID, title, benefit, scope, acceptance, and verification route. No candidate implementation is authorized yet. Proposal content and original evidence snapshot are immutable; identical proposal retries are idempotent, conflicting retries fail.

## Selection (`select --selection FILE`)

```json
{
  "proposal_id": "proposal-<returned ID>",
  "reply_context": "<latest_reply.context from status>",
  "reply_digest": "<latest_reply.digest from status>",
  "selected_ids": ["summary"],
  "presented": true,
  "interpreted": true
}
```

`status --context CONTEXT` returns `latest_reply` with session, turn, context, and SHA-256 of the exact UTF-8 genuine prompt, without storing the prompt. A new selection must bind the latest genuine reply from the owning session, after the proposal. `presented` attests actual presentation of the returned list; `interpreted` attests the agent interpreted that reply as selecting those IDs. Optional `prompt` verifies its digest but is never persisted. The agent is trusted for semantic interpretation and these attestations; no NLP parser, transcript parser, or second confirmation is used. Empty IDs record decline. IDs must be a unique subset of the immutable proposal. Identical normalized selection replay is a no-op even after later turns; conflicting replay fails.

Exact Stop continuation reason texts generated by this hook are registered by digest, and excluded from genuine UserPromptSubmit capture. No arbitrary natural-language prompt heuristic is used. Real hooks must supply UserPromptSubmit `prompt` and `turn_id`.

## Progress (`advance --update FILE`)

```json
{
  "proposal_id": "proposal-<returned ID>",
  "item_id": "summary",
  "status": "progress",
  "evidence": "The changed hook source is ready for the disposable CLI check.",
  "checkpoint": {"path": "tools/solidworks-mcp/codex_hooks/selected_work.py", "sha256": "<current SHA-256>"}
}
```

Only selected IDs may advance. `status` is exactly `progress|verified|pending_live|blocked|paused|cancelled|resume`; every update needs bounded nonempty `evidence`. `progress` requires a current local `checkpoint` file (maximum 2 MB), or `changed_sources` as below. No-progress detection uses observed file hash fingerprints and verified phase, never narration/timestamps/repeated updates. A checkpoint can be a real test-result artifact as well as source. At most 128 distinct checkpoints are retained per item.

`pending_live` and `blocked` preserve unfinished work with the actual blocker in `evidence`, and do not block Stop. `paused` and `cancelled`, or resuming those states, additionally require `user_requested: true`, `reply_context`, and `reply_digest` bound to the latest genuine reply. `resume` of stalled work may carry the same explicit user control fields. A genuinely changed progress checkpoint also resumes stalled work automatically. Merely writing `resume` or new narration cannot reset a stall.

## Verified hook/CLI result

```json
{
  "proposal_id": "proposal-<returned ID>",
  "item_id": "summary",
  "status": "verified",
  "evidence": "The disposable protocol/CLI check returned the new persisted summary.",
  "changed_sources": [{
    "path": "tools/solidworks-mcp/codex_hooks/selected_work.py",
    "before_sha256": "<old SHA-256, distinct from current>",
    "sha256": "<current SHA-256>"
  }],
  "verification": "outputs/checks/summary-verification.json"
}
```

The verification artifact:

```json
{
  "proposal_id": "proposal-<returned ID>",
  "item_id": "summary",
  "status": "passed",
  "route": "hook_cli",
  "source_hashes": {"tools/solidworks-mcp/codex_hooks/selected_work.py": "<current SHA-256>"},
  "capability": "Persist bounded audit summary",
  "invocation": "Ran the real hook/CLI protocol against a disposable project.",
  "before_behavior": "status omitted the summary.",
  "observed_behavior": "status returned the expected summary after a fresh CLI process."
}
```

`changed_sources` contains 1–64 Python sources inside `tools/solidworks-mcp`, each with distinct old/current SHA-256. Actual hashes must match current disk files. Evidence artifacts are JSON objects inside ROOT, maximum 200 KB. The route, proposal ID, item ID, all current source hashes, nonempty invocation/capability, and distinct before/observed behavior must match. A source edit or ticket is not verification.

## Verified live capability result

Use the same verified update and artifact with `route: "live_tool"` and `tool: "inspect"` matching the original candidate. Add these update fields:

```json
{
  "source_check": {
    "catalog_digest": "<current catalog digest>",
    "tool": "inspect",
    "source": "tools/solidworks-mcp/solidworks_mcp/ops.py",
    "sha256": "<current capability-source SHA-256>"
  },
  "live_check": "outputs/checks/inspect-live.json"
}
```

The live artifact:

```json
{
  "proposal_id": "proposal-<returned ID>",
  "tool": "inspect",
  "availability": "available",
  "source_hashes": {"tools/solidworks-mcp/solidworks_mcp/ops.py": "<current capability-source SHA-256>"},
  "evidence": "The reloaded connected named tool was invoked on a disposable copied model."
}
```

The named atomic source must be in the current source catalog and changed sources. Both behavioral verification and live artifact bind current source hashes. Source visibility, reload claims, offline checks, and tickets alone cannot satisfy live completion. There are no invented UI fallback IDs for non-UI improvements.

## Opaque CAD operation (`operation-note --note FILE`)

```json
{
  "operation": "Read the active model after the authorized script",
  "route": "opaque_cli",
  "outcome": "completed",
  "evidence": "The script returned the expected active-document identifier."
}
```

All four fields are nonempty bounded text, at most 1,200 characters each. Optional `timing_ms_total` and `response_bytes` record actual opaque-CLI measurements; both are nonnegative finite numbers up to 1e12, and bytes must be an integer. Omitted measurements remain unknown. Notes have deterministic `op-...` IDs based on the four required fields, deduplicate identical notes, and establish CAD activity independently of UI. Maximum 128 notes per context. This records evidence only; it never runs a script. UI fallback classification continues to use `fallback-note` with its existing schema.

## Hooks, continuation, metrics

All recognized CAD events, explicit opaque notes, and explicit preflight operations require reflection in version 2. `finish` cannot satisfy reflection, and `post-work` is rejected for new contexts so it cannot bypass selection. Proposals with candidates wait without blocking Stop; no-candidates and declined selections finish that request's reflection. Reasoned unfinished-CAD deferrals also do not block Stop.

Runnable selected work continues across repeated `stop_hook_active` events with no fixed retry ceiling while meaningful file/verified evidence advances. Three consecutive unchanged Stop boundaries record `needs_review`/`stalled`; never completion. SessionStart and UserPromptSubmit remind the owning session of unfinished work. Other sessions are not silently assigned ownership.

CAD validation requires explicit `preflight --context CURRENT --operations FILE --validation-of ORIGINAL_SELECTED_CONTEXT`. The owner must have unfinished selected work in the same session; ordinary preflight omits this option. Validation still requires current catalog coverage before CAD. Calls and `operation-note` under this explicitly bound validation context attach evidence to the original selected context and do not create recursive proposals. A new user CAD request uses ordinary preflight and receives its own reflection even while earlier selected work remains unfinished. Additional unselected scope requires its own proposal/selection.

Normal observations deduplicate call IDs and exclude wrapper-only duplicates. `status.metrics` reports `call_count`, `known_timing_ms_total`, `missing_timing_count`, `response_bytes_total`, and `missing_response_bytes_count`. Known `timing_ms.total` is collected from normal MCP response shapes. Missing responses and timing stay unknown; byte counts are serialized UTF-8 bytes, not tokens. Within an unfinished selected batch, current source hashes for previously verified items are checked again by status/advance/Stop; source drift reopens that item for behavioral revalidation, including when another selected item edits a shared file. Once all selected items verify against current hashes, a completed snapshot seals that batch as historical; unrelated future source edits do not resurrect it.
